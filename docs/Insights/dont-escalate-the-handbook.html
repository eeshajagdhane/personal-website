Don't escalate the handbook

I stacked a café operations console in four layers — plan and data, skill contracts, tools and RAG, then a review UI. The extract is a drink order. The point is the gate: a customer-facing recommendation does not move until a human says so, and a safety detector that reads the handbook will escalate the handbook.

The problem

A barista already does the work: check the case, glance at the schedule, guess the rush, recommend something in stock, catch a missing size, and notice the word “allergy.” The pieces exist. They just live in different heads, binders, and walks to the back.

I wanted one console for those three moments in a shift — manager readiness, a drink recommendation, and an order that is complete before it is built — with evidence attached and a human still in the way of anything a customer hears. I built it with teammates. The current example uses the public Starbucks menu plus simulated store data. No proprietary operations data is in the repository.

What each layer is for
The interesting design is not “add an LLM.” It is what the coworker is not allowed to do.

The detector was reading the handbook

Allergy language always escalates. That rule is correct. The first version of the check scanned the whole workflow output, including RAG filenames and snippets. The file dietary_allergen_guidance.md contains the word allergen. A dairy-free request retrieved that file. The detector treated the handbook as the customer.

Benign drinks were routed to “escalate to allergen review.” Real allergies were still caught — and so was every request that happened to pull the policy doc. Alert fatigue is how a safety rule dies.

Should this escalate?
Same rules as the tests. The old scan read the handbook. The current scan reads the customer.

The fix is a smaller scan, not a weaker rule. Face validity now reads the customer's words, the warnings, and the review-queue labels. It does not stringify RAG metadata. Real allergy language still forces needs_review and escalate. The handbook does not.

Customer-facing steps are designed to land in needs_review. That is not a failed run. Approve, Edit, Reject + Rerun, and Escalate are part of the process. The console records those actions in an audit log. Reject + Rerun does not yet feed a corrected input back into the orchestrator — the button is a log entry, not a loop.

What a run actually does

Manager readiness aggregates rush, staffing, inventory, and promotions into one briefing. A recommendation scores the menu against preferences, down-ranks anything whose key ingredient is low, and retrieves policy docs. The order builder parses size, temperature, milk, and extras, then asks a follow-up when a field is missing.

No LLM runs at serving time. Tools are Python functions. RAG is keyword scoring over twelve markdown files. Tests run offline. The skill files describe the spoken recommendation those tools would feed; the console currently shows the structured envelope instead.

The technical layer

For readers who want the mechanics
Why skills are contracts, not the runtime

Each SKILL.md says when to recommend, which tools to call, which SOP to retrieve, and what the spoken line should contain. The orchestrator does not load those files. It calls the tools and RAG itself and returns JSON the UI can render. That is honest: the contracts are the design; the running path is tools plus retrieval plus a human gate.

Wiring a skill adapter later is a thin generation step on top of the same envelope. The gate stays. The model, if it ever speaks, still cannot skip Approve.

What the allergy scan is allowed to read

The old check stringified final_output. That object embeds retrieved document titles and snippets, so a filename with “allergen” in it was indistinguishable from the customer typing the word. Two regression tests now pin the split: a benign dairy-free request must not escalate, and a request that says “nut allergy” must.

Warnings and review-queue labels are still in the scan, because the orchestrator already copies a real allergy hit into those fields. The handbook never should have been a signal.

What the tests actually pin down

Ninety-five tests, all local. Tools, retrieval, four orchestrator workflows, face validity, and Flask routes. A missing size produces a follow-up question. Stale inventory falls back to the latest prior snapshot and says so. Dairy-free search uses a vegan heuristic and labels it as a heuristic. Prep notes always include “prepared individually.”

The suite is the spec. The panels above are the same rules with the numbers filled in.

What I'd do differently

Close the review loop. Reject + Rerun should send corrected input back through the orchestrator. A button that only writes to a log is not a loop.

Keep session state for missing fields. The order builder already asks “What size?” The answer should complete the same order instead of starting a new run.

Speak from the skill contract only after the tools have gated. Natural-language confirmation is useful. It is not a substitute for the structured parse, the inventory check, or Approve.

What this case taught me

Stack the process before you stack the model. Plan, contracts, tools, then a console. Each layer has a job. Skipping to a chatbot would have hidden whether inventory, rush, and allergy rules actually fired.

A safety detector that reads the handbook will escalate the handbook. The word “allergen” in a policy filename is not a customer risk. Scanning the customer's words is. Those have to be different inputs.

Needs-review is a designed state, not a failure. If the coworker can talk to a customer without Approve, the evidence package is decoration. The gate is only a gate if load — here, speech — is allowed to refuse.
